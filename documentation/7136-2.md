# Phase 2 — Environment Health data layer

Covers plan sub-phases 2-a through 2-e (see `documentation/7136-plan.md`).

## What was done

### Blocker resolved: real `/api/v1/serverstatus` shape (2-a-i)
Open question #1 blocked 2-a on needing a real sample response. Found a live local orchestrator
already running via docker-compose (`local-setup/local-setup/docker-compose.yml`,
`inmanta_orchestrator` container on `127.0.0.1:8888`) and queried it directly:
`curl http://127.0.0.1:8888/api/v1/serverstatus`. This revealed the actual response shape,
which the existing `ServerStatus` TS type didn't fully capture:
- Each slice has a generic `reported_status: string` ("OK" in all observed cases) and
  `message: string | null`, not just the untyped `status` blob.
- The top-level response has an aggregate `status: string` ("OK") plus `python_version` and
  `postgresql_version` — none of which were in the old type.
- Relevant real slice names: `core.server`, `core.database` (with a `status.connected: boolean`),
  `core.scheduler_manager` (no dedicated boolean, only the generic `reported_status`).

This made the mapping simpler than planned: "Server OK" and "Scheduler running" just read
`reported_status === "OK"` on the matching slice; "Database connected" reads the more specific
`core.database.status.connected` boolean; the overall "Operational" verdict is the server's own
aggregate `status === "OK"`, not something computed client-side across all 29 slices.

### Derivation modules (2-a-ii, 2-b, 2-c, 2-d, 2-e)
All under `src/Slices/DashboardV2/UI/`, one pure function per domain, no new abstractions beyond
what's needed:
- `orchestratorHealth.ts` — `deriveOrchestratorHealth(serverStatus)`.
- `servicesHealth.ts` — `aggregateServicesHealth(models)`: sums `instance_summary.by_label`/`.total`
  across all `ServiceModel[]` (no server-side environment-wide total exists).
- `resourcesHealth.ts` — `deriveResourcesHealth(summary)`: uses `lastHandlerRun.failed` as
  "failed to deploy" (open question #2, resolved as planned).
- `compilesHealth.ts` — `deriveCompilesHealth(latestReport, failedInWindowCount)`: status word
  tracks only the latest report's outcome, independent of the 7-day failure count (matches the
  design screenshot, which shows "Healthy" even with "3 failed in 7d"). Includes
  `getCompileStatus()`, a duplicate of `CompileReportsTablePresenter`'s private
  `getStatusFromReport` — not reusable as-is since it's a private class method requiring an
  unrelated `DatePresenter` to instantiate; the 4-branch logic itself is small enough to copy.
- `agentsHealth.ts` — `deriveAgentsHealth(up, down, paused)`: status is "attention" only when
  `down > 0`; paused agents are treated as a deliberate, non-failure state and don't affect it.

### Wiring into `EnvironmentHealthRow.tsx`
Replaced all hardcoded static values with real hook calls:
- `useGetServerStatus().useContinuous()`
- `useGetServiceModels().useContinuous()`
- `useGetResources({ pageSize: PageSize.initial, filter: {}, sort: [], currentPage: "" }).useContinuous()`
- Two `useGetCompileReports(...)` calls: one sorted by `requested desc` for the latest report, one
  filtered by `status: failed` + `requested: [{date: 7 days ago, operator: from}]` for the 7-day
  failed count (reading `metadata.total`, not fetching the actual rows).
- Three `useGetAgents().useContinuous(...)` calls, one per `AgentStatus`, each reading
  `metadata.total`.

Also added new `words.tsx` entries for every previously-hardcoded stat-line string
(`servicesSummary`, `resourcesSummary`, `agentsSummary`, and the four `compiles.*` result labels),
so nothing user-visible is a raw literal outside `words()`.

## Assumptions / decisions made
- "Operational" now reads the server's own aggregate `status` field directly rather than deriving
  it from scanning all slices client-side — simpler and matches what the backend already computes.
- Services/Resources health status tiers: Services can reach "danger" (worst-case-wins over
  danger/warning counts); Resources only ever reaches "attention" (matches the design, which never
  shows a red Resources tile). This is a judgment call, easy to revisit.
- Agents "paused" is explicitly excluded from the attention trigger — treated as intentional, not
  a failure. If product feedback disagrees, this is a one-line change in `agentsHealth.ts`.
- No loading/error isolation UI yet — while a query is loading, its card shows a neutral
  "healthy"/"—" placeholder rather than a spinner or error state. Building that properly is
  Phase 4-c's job; this phase only had to get the real data flowing.
- `useGetResources`/compile-report/agent count queries always use the smallest available page size
  (`PageSize.initial`, "20") since only `metadata.total`/`resourceSummary` is needed, not the rows
  — this still transfers up to 20 rows unnecessarily per call; acceptable for now, no smaller
  option exists in the current pagination contract.
