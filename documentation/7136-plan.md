# Ticket 7136 — Dashboard V2: Implementation Plan

## 1. Scope

Build a new **Dashboard V2** page in web-console. The full page design is now available and consists
of five stacked blocks:

1. **Environment health row** — header (title, subtitle, "Updated X min ago", "Last 7 days" range
   control, "Refresh" button) + an **Orchestrator** summary card (icon, env name, "Switch" link,
   "Operational" verdict, 3-item checklist) + four **health columns** (Services, Resources, Compiles,
   Agents), each a status word + 1–2 stat lines.
2. **Latest compile reports** panel — title + "N failed · 7d" badge + "View all compile reports"
   link, and a list of the most recent compile reports (status icon, trigger-type label, duration or
   "Running…", relative time, "View progress"/"View report" link).
3. **Orchestrator** detail card (left) — condensed version of the existing Status page: edition,
   version, license, Python/PostgreSQL versions, extensions list, "Open full Orchestrator Status
   page →" link, "Operational" badge.
4. **Resource Manager** detail card (right, alongside #3) — three labeled stacked bars (Compliance /
   Deploy result / Blocked) plus a 4-tile stat row (Deploying now / Deployed OK / Failed /
   Non-compliant).
5. **Orchestration Engine** panel — segmented control (Compile rate / Compile time / Waiting time), a
   4-stat header row (Compiles / Failed / Avg compile / Avg waiting), and a single line/area chart for
   the selected metric over the last 7 days.

**Decision**: Dashboard V2 is a **new, separate route/slice** (`DashboardV2`, path `/dashboard-v2`),
coexisting with the current `Dashboard` slice (`src/Slices/Dashboard/`, chart-only). It is **not**
replacing the current Dashboard or the default landing route in this plan — that's a follow-up
decision (it would touch hardcoded `"Dashboard"` fallbacks in `PrimaryRouteManager.ts` and
`EnvSelector/Provider.tsx`).

## 2. Endpoint / hook reuse (constraint: no new backend work)

Confirmed via codebase research — **every block on the page is servable from existing, already-wired
hooks**. No new backend endpoint is required anywhere on this page.

| Block | Hook (existing) | Endpoint | Notes |
|---|---|---|---|
| Orchestrator health card | `useGetServerStatus` (`src/Data/Queries/Slices/Server/GetServerStatus/`) | `GET /api/v1/serverstatus` | Generic `slices[].status` blob — need specific key mapping (see open Q1) |
| Services health column | `useGetServiceModels` (`.../Slices/Service/GetServiceModels/`) | `GET /lsm/v1/service_catalog?instance_summary=True` | Sum `instance_summary.by_label`/`.total` across all `ServiceModel[]` |
| Resources health column | `useGetResources` (`.../Slices/Resource/GetResources/`) | GraphQL `resourceSummary` field | Pick mapping for "failed to deploy" (see open Q2) |
| Compiles health column | `useGetCompileReports` (`.../Slices/Compilation/GetCompileReports/`) | `GET /api/v2/compilereport` | 2 filtered calls (latest report; failed-count via `metadata.total`) |
| Agents health column | `useGetAgents` (`.../Slices/Agents/GetAgents/`) | agents list endpoint | 3 filtered calls (one per `AgentStatus`), reading `metadata.total` each |
| "Switch" env trigger | `useGetEnvironments`, `environmentHandler`, `EnvSelector*` (`src/UI/Root/Components/Header/EnvSelector/`) | existing env endpoints | No standalone trigger exists outside `Header` (see open Q3) |
| Latest compile reports panel | `useGetCompileReports` (same hook, `sort desc`, `pageSize ~5`) | same as above | Reuses `CompileReportsTablePresenter.getStatusFromReport()` derivation logic |
| Orchestrator detail card | `useGetServerStatus` (same hook/params as health card) | same as above | React Query dedupes identical calls automatically — one network request serves both cards |
| Resource Manager card | `useGetResources` (same hook/params as health column) | same as above | Same dedup benefit; also reuses `Resource.CompoundStateSummary` shape directly |
| Orchestration Engine chart | `useGetMetrics` (`src/Data/Queries/Slices/Dashboard/GetMetrics/`) | `GET /api/v2/metrics` (existing, already powers current Dashboard) | Series already exist: `orchestrator.compile_rate`, `orchestrator.compile_time`, `orchestrator.compile_waiting_time` (`Dashboard/Core/Domain.ts`) |

## 3. Open questions / decisions to resolve during the relevant phase

1. **Server status slice/key names** (blocks Phase 2-a): `ServerStatus.slices[].status` is an untyped
   `Record<string, unknown>` — confirmed via `StatusList.tsx` that today's Status page renders it
   generically (no existing code maps specific keys to "Database connected"/"Scheduler running").
   Need a sample `/api/v1/serverstatus` JSON response from a running orchestrator, or a backend
   source lookup, before the mapping can be written.
2. **"Failed to deploy" semantic mapping** (Resources health column): decide between
   `lastHandlerRun.failed` and `compliance.non_compliant`. Recommendation: `lastHandlerRun.failed`
   for the health column (direct read of "a deploy attempt failed"); note the Resource Manager card
   (block 4) shows **both** as separate stat tiles, so this only matters for the terser health-column
   wording. Confirm during Phase 2-c.
3. **Env-switch trigger reuse** (Orchestrator health card): `EnvSelector` dropdown state today lives
   inside `Header.tsx`. Needs either lifting shared state into context, or a new lightweight trigger
   reusing `environmentHandler`/`useGetEnvironments` + the existing `EnvSelector` menu body. Decide in
   Phase 3-b.
4. **Date-range control scope**: only the Compiles "failed in N days" stat (and the Orchestration
   Engine panel, block 5) is genuinely window-dependent; the other three health columns are
   point-in-time snapshots regardless of range.
5. **Agent counts at scale**: 3 filtered requests (one per status, reading `metadata.total`) over one
   bulk fetch + client reduce, to avoid an incorrect total under pagination.
6. **Orchestration Engine header stats source** (block 5): "Compiles"/"Failed" need exact integers —
   recommend sourcing these from the same compile-report count queries as Phase 2-d/Phase 5 (`metadata.
   total`, deduped by React Query), not from the bucketed/averaged `useGetMetrics` series. "Avg
   compile"/"Avg waiting" map naturally to averages of the `orchestrator.compile_time` /
   `compile_waiting_time` series instead. Confirm during Phase 8-a.
7. **"Refresh" button scope**: the design shows a single top-right Refresh affordance for the whole
   page. Recommendation: it invalidates/refetches every Dashboard V2 query (all 5 blocks), not just
   the Environment Health row. Confirm during Phase 9-b.
8. **Query dedup reliance**: several blocks intentionally call the *same* hook with the *same*
   parameters as another block (Orchestrator health card ↔ Orchestrator detail card; Resources health
   column ↔ Resource Manager card; Compiles health column ↔ Latest Compile Reports failed-count
   badge). React Query dedupes identical query keys automatically — implementers must keep params
   identical to get a single network request for free, rather than building custom cross-component
   data sharing.

## 4. Phase breakdown

### Phase 1 — Slice scaffolding & shared primitives
- **1-a**: Register the `DashboardV2` slice skeleton: `src/Slices/DashboardV2/{index.tsx, Core/Route.ts, UI/index.tsx, UI/Page.tsx}`; add `"DashboardV2"` to `kinds` in `src/Core/Domain/Route.ts`; wire into `PrimaryRouteManager.ts` (`routeDictionary`) and `PrimaryPageManager.tsx` (`pageDictionary`); add a nav entry in `Group.ts`. Page renders an empty `PageContainer` shell so routing/nav can be verified before any real content exists.
- **1-b**: Shared primitives for the Environment Health row: a status indicator (colored dot + word, icon-paired not color-only, for accessibility) and the card/grid container matching the screenshot's layout (orchestrator card + 4 divided columns). Static props only, no live data.
- **1-c**: Page-level layout scaffold for the remaining four blocks — `Section`-style wrapper components in placement/order per the full design (Latest Compile Reports panel; two-column Orchestrator + Resource Manager row; Orchestration Engine panel), rendered with static placeholder content so the whole page's shape is visible before each block gets real data in later phases.

### Phase 2 — Environment Health data layer (one hook/aggregation per domain, independent of each other)
- **2-a**: Orchestrator status.
  - **2-a-i**: Resolve open Q1 (real slice/key names) — needs a sample response or backend lookup before coding the mapping.
  - **2-a-ii**: Derivation hook on top of `useGetServerStatus` producing `{ operational: boolean; serverOk: boolean; databaseConnected: boolean; schedulerRunning: boolean }`.
- **2-b**: Services health aggregation — reducer over `useGetServiceModels()` summing `instance_summary.by_label` (`success/warning/danger`) and `.total` across all services.
- **2-c**: Resources health aggregation — selector over `useGetResources()`'s `resourceSummary`; resolve open Q2 and implement the "failed to deploy" count.
- **2-d**: Compiles health aggregation — two composed `useGetCompileReports` calls (latest report via `sort desc, pageSize 1`; failed-in-window count via `filter.status=failed` + `filter.requested ge <window start>`, reading `metadata.total`). Reuses existing `getStatusFromReport` logic for the "last result" label.
- **2-e**: Agents health aggregation — three filtered `useGetAgents` calls (`status: [up]`, `[down]`, `[paused]`), each reading `metadata.total`; sum for the overall total.

### Phase 3 — Environment Health UI components
- **3-a**: `OrchestratorHealthCard` — icon, env name, "Operational" verdict badge, 3-item checklist, wired to Phase 2-a's hook.
- **3-b**: Environment "Switch" trigger — resolve open Q3; implement a reusable trigger usable from the orchestrator card.
- **3-c**: The four health columns (`ServicesHealthColumn`, `ResourcesHealthColumn`, `CompilesHealthColumn`, `AgentsHealthColumn`) — thin data-wiring wrappers around the Phase 1-b generic status-column primitive, wired to their respective Phase 2 hooks.
- **3-d**: `EnvironmentHealthRow` container — composes the header (title, subtitle, "Updated X ago" timestamp, date-range control, refresh button) with the orchestrator card + 4 columns in the Phase 1-b grid.

### Phase 4 — Environment Health assembly & polish
- **4-a**: Wire the row-level refresh affordance to refetch/invalidate the Environment Health queries; implement the "Updated X min ago" relative timestamp. (Scope may be widened to page-global in Phase 9-b.)
- **4-b**: Wire the date-range control (default last 7 days) to feed the Compiles window query only (open Q4); local component state, no persistence needed.
- **4-c**: Per-card loading/error/partial-failure handling — one card's query failing must not blank the others; empty-state handling (e.g. zero agents/services).
- **4-d**: `words.tsx` i18n entries under a new `dashboardV2.environmentHealth.*` namespace; accessibility pass (aria-labels on status indicators, keyboard reachability of "Switch"/refresh/range controls).

### Phase 5 — Latest Compile Reports panel
- **5-a**: Data — hook for "latest N compile reports" (`useGetCompileReports`, `sort desc`, `pageSize ~5`); reuse `CompileReportsTablePresenter.getStatusFromReport()` for status/icon derivation; reuse Phase 2-d's failed-in-7d query for the badge count (same query key ⇒ deduped, no extra request).
- **5-b**: UI — `LatestCompileReportsPanel`: header (title + failed-count badge + "View all compile reports" link → existing CompileReports route), row list (status icon, trigger-type label, duration or "Running…", relative time, "View progress"/"View report" link → existing CompileReportDetails route per report id).

### Phase 6 — Orchestrator detail card
- **6-a**: Reuse investigation — review `Status/UI/StatusList.tsx` / `StatusItem.tsx` (confirmed: `toDetails()` generically renders product fields + extensions + slices) to decide which fields to lift into a condensed card (edition/version/license/Python/PostgreSQL + extensions) vs. what's specific to the full Status page (per-slice detail, features) and gets omitted here.
- **6-b**: UI — `OrchestratorDetailCard`, sourced from the same `useGetServerStatus` call as Phase 2-a (deduped), with an "Open full Orchestrator Status page →" link to the existing `/status` route.

### Phase 7 — Resource Manager card
- **7-a**: Data — reuse `useGetResources` resourceSummary from Phase 2-c (deduped, same query/params).
- **7-b**: UI — new `StackedStatusBar` presentational primitive (reused 3×: Compliance / Deploy result / Blocked), each a labeled multi-segment horizontal bar + legend, built from `resourceSummary.compliance` / `.lastHandlerRun` / `.blocked`.
- **7-c**: UI — 4-tile stat row (Deploying now / Deployed OK / Failed / Non-compliant) below the bars, sourced from `resourceSummary.isDeploying.true` / `.lastHandlerRun.successful` / `.lastHandlerRun.failed` / `.compliance.non_compliant`.

### Phase 8 — Orchestration Engine chart panel
- **8-a**: Data — reuse existing `useGetMetrics` for the three series `orchestrator.compile_rate` / `compile_time` / `compile_waiting_time`; resolve open Q6 (header stats sourced from compile-report count queries for exact integers, metrics-series averages for the two "Avg" stats).
- **8-b**: UI — new segmented control (Compile rate / Compile time / Waiting time) driving a single chart view, reusing the existing `LineChart`/`GraphCard` building blocks from `Dashboard/UI/Charts` rather than the current one-graph-per-metric `Section` layout (`Dashboard/UI/Section.tsx`).

### Phase 9 — Full-page assembly & polish
- **9-a**: Final section order/spacing per design; responsive layout for the two-column (Orchestrator + Resource Manager) row.
- **9-b**: Resolve open Q7 (Refresh button scope) — implement page-wide query invalidation if confirmed.
- **9-c**: Per-section loading/error isolation across the whole page, extending Phase 4-c's principle to blocks 2–5.
- **9-d**: i18n entries for all new sections (`dashboardV2.compileReports.*`, `dashboardV2.orchestrator.*`, `dashboardV2.resourceManager.*`, `dashboardV2.orchestrationEngine.*`) + accessibility pass across the full page.

### Phase 10 — Testing
- **10-a**: Unit tests for new aggregation/derivation logic (compile report status/duration formatting, resource bar segment math, metrics-series-to-chart mapping, orchestrator checklist mapping, agent/service count reducers) using MSW-mocked responses for edge cases (zero counts, all-failed, missing slice keys).
- **10-b**: Component tests per block covering loading / success / partial-error render states.
- **10-c**: Cypress smoke test — navigate to `/dashboard-v2`, assert all 5 blocks render and populate with mocked data.

## 5. Re-split review

Re-checked each phase against "should this split further?":
- Phase 2's five sub-items are single-hook, independent units — correctly granular. 2-a split into
  -i/-ii because -i is a blocking research/verification step with an external dependency (real API
  sample), distinct in kind from the coding step in -ii.
- Phase 3's four sub-items are single-component units; 3-b split out from 3-c because it touches
  shared `Header`-adjacent code (higher risk) rather than a fresh domain component.
- Phase 6 mirrors Phase 2-a's investigation/build split, since the condensed-card field selection is a
  design decision distinct from implementing it.
- Phase 7 split into three (data / bar primitive / stat tiles) because the `StackedStatusBar` is a new
  reusable primitive worth isolating from the simpler stat-tile row that consumes the same data.
- Phase 8 kept at two (data+stats vs. UI+control) — the stat-source decision (Q6) is the only
  non-mechanical part of 8-a, not worth a further split.
- Phase 9 and 10 sub-items are each independently shippable/testable — no further split needed.
- Phase 1 kept at three sub-items (routing scaffold, Environment Health primitives, full-page layout
  scaffold) — each is small and low-risk; 1-c was added (not split further) once the full-page design
  became available, so the whole shape is visible before phases 5–8 fill it in.

## 6. Process notes

- After each phase, a short note goes to `documentation/<phase-id>.md` (e.g. `documentation/7136-2a.md`)
  describing what was done, files changed, and assumptions made.
- After each run, context-window fullness (low/medium/high) will be reported, with a recommendation to
  split the next phase further if high.
- No coding starts until this plan is confirmed.
